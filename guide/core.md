# 内核

3m-ui 管理固定版本的 **Mihomo** 二进制。可在面板「内核」页，或通过 `systemctl` / `3m-ui` 命令启动、停止、重启与更新。

- 完整安装包 / Docker 镜像内含 pinned 内核；仅面板二进制的高级安装需自备兼容内核
- 内核重载期间，面板 API 可能短暂不可达；节点 / 用户往往已写入数据库，稍候刷新即可

## 运行日志

面板「日志」页分为两个 Tab，对应不同 API：

| Tab | API | 内容 |
|-----|-----|------|
| **Mihomo 核心** | `GET /api/v1/mihomo/logs` | 核心进程 stdout/stderr（内存环形缓冲） |
| **面板进程** | `GET /api/v1/system/panel-logs` | 面板 `log` 输出（ACME、启动、错误等，带 `[panel]`） |

均需管理员 JWT。二者**不会**混在同一接口里。

## 独立更新 Mihomo

管理员可在 **内核 → 检查更新** 中选择官方稳定版或 Pre 版，或 **恢复上一版本** 回到已保存的二进制。此过程**独立于面板**更新；检查发布列表不会自动安装。会查询最近约 30 条 GitHub Release，排除草稿与无 SHA-256 摘要的产物。支持 Linux **amd64**（baseline v1）与 **arm64**。

更新器仅从 GitHub `MetaCubeX/mihomo` 下载，校验 GitHub 提供的 SHA-256，检查可执行文件版本，并在停止旧核心前对当前配置做测试。压缩包上限 64 MiB、解压后的二进制上限 128 MiB，并设有请求与校验超时。

对正在运行的核心，更新器会核对现有监听、停止旧进程、启动候选二进制，并核验新进程与已知的本地监听套接字；切换失败会恢复原有可执行文件与运行状态。若核心原本处于停止状态，安装后仍保持停止，只做可执行文件与配置校验。更新不测试公网连通性、防火墙规则与协议握手；本地套接字检查也不覆盖不受支持的 listener 传输方式。较旧的发行版可能拒绝较新的配置字段，配置校验会在停止运行中的核心之前拒绝该更新。更多说明见 [核心更新](./core-updates)。

## 持久选择与恢复

内置的 `mihomo.binary` 始终作为不可变回退版本。受管二进制存放在 `config.yaml` 同级的 `cores/` 目录，通常为 `/var/lib/3m-ui/mihomo/cores/`。目录内容为：

- `mihomo-<sha256>`：当前版本与上一版本的可执行文件
- `selection.json`：schema 1，记录 active 与 previous 的 version / checksum
- `job.json`：最近一次更新结果或中断的任务
- `update.lock`：更新与部署工具使用的协作式排他锁

首次切换前，内置核心会被复制到该目录，因此后续面板 / 镜像升级后上一版本仍然存在。选定版本只在校验与运行时检查全部通过后原子写入；切换未完成时重启，会选中上一次已提交的版本。选定二进制损坏或缺失时会明确报错，而不会静默回退到镜像内置版本；损坏的选择元数据需从备份恢复整个目录。

常规 Docker 数据卷已包含该目录，无需 Docker socket、root 权限或可写镜像文件系统；重建容器时保留该数据卷。原生安装需保证面板服务对该目录可写、可执行（随附的 systemd unit 已允许写入数据目录）；`noexec` 挂载会导致核心更新失败。不要在多个面板实例之间共享同一数据目录。

面板升级必须兼容 selection schema 1 并保留已选二进制。`distribution/core-update.json` 向部署工具声明该存储契约。替换面板前，部署工具可在备份、切换与运行时检查期间对 `cores/update.lock` 持有 `flock(LOCK_EX)`；锁被占用时面板内更新器返回 409。请备份整个核心配置目录（含两个二进制与选择元数据），并在部署后分别验证当前核心版本、本地监听状态与面板 HTTP 健康检查。

## API

全部接口沿用现有的管理员认证。

| Method | Endpoint | Result |
| --- | --- | --- |
| GET | `/api/v1/mihomo/releases` | 近期稳定版与 Pre 版，含可用的平台产物与 release notes |
| GET | `/api/v1/mihomo/update` | 能力、持久化 / 回滚状态与最近任务 |
| POST | `/api/v1/mihomo/update` | JSON `{"version":"v1.19.31"}`；返回 HTTP 202 与已接受的任务 |
| POST | `/api/v1/mihomo/update/rollback` | 返回 HTTP 202 与恢复上一版本的任务 |

POST 只接受版本号，不接受任意下载 URL 或可执行文件路径。并发更新或部署锁被占用时返回 HTTP 409。轮询 GET `/mihomo/update` 直到任务为 `succeeded` 或 `failed`；关闭页面不会取消任务。失败任务会给出失败阶段、错误与 `rolled_back` 结果。更新期间会拒绝启动 / 停止 / 重启与配置变更，避免排队的操作在切换完成后意外生效。已提交到数据库的用户与 listener 绑定变更，会在更新成功或失败后依据最新数据库重新生成配置来对齐；其 API 响应仍可能返回临时的 busy 错误。手动回滚不要求当前核心健康，只校验已保存的目标并在启动后检查其监听。

## 官方 Pre 版本

下拉框把官方 `Prerelease-Alpha` 渠道标为 **Pre**，并显示具体的 `alpha-<commit>` 构建。默认仍是稳定版，选择 Pre 需显式操作；其他 prerelease 渠道与替代 Go 构建均被排除。发布列表缓存 1 分钟。安装时会重新解析滚动 tag，若构建已变化则拒绝安装，而不是静默装上另一个版本；压缩包校验和与可执行文件版本必须与解析到的元数据一致。选定构建与内容哈希会被持久化，因此即使上游 Pre 发布更新，重启与回滚仍使用完全相同的可执行文件。

POST 接受显示出来的构建，例如 `{"version":"alpha-dca26db"}`，而不是滚动 tag；若构建已被替换，请重新检查更新。Pre 版本可能拒绝现有配置，稳定版与 Pre 之间的切换同样适用前述校验与恢复检查。

## 自定义核心路径

可设置环境变量 `THREE_M_UI_MIHOMO_BINARY=/绝对路径/to/mihomo`。自定义核心需自行验证兼容性并做好备份；完整发行包只承诺清单中的配套版本。
